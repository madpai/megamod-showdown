# Post-N3 order: desktop testing support and X1

**Status:** decision memo, 2026-09-26. Evidence: [`DESKTOP_AGENT.md`](../DESKTOP_AGENT.md) says Steps 1–4 and shared `hta_session_tick` exist; `megamod-join` can join by world and run headless, while `megamod-match` runs bots headless and `megamod-sandbox` has a control/event harness. The full local-player control loop still has Android coupling. The emulator has covered real Blood Gulch and imported-map LAN matches. These are useful test paths but do not yet give convenient two-client, late-join X1 automation.

| Order | Testing benefit | Architecture/refactor cost |
| --- | --- | --- |
| **A. Full Step 5 desktop client, then X1** | Best manual two-window play, native menus and audio; straightforward visual host/join diagnostics | Moves all player/UI/audio behavior before the world-event contract is known. It risks making the frontend appear required for engine changes and later revisiting input, collision and snapshot wiring after X1. |
| **B. X1 immediately, then Step 5** | Keeps engine work moving and can use headless host plus emulator/`megamod-join` | Late join, button intent and two-client state are harder to drive and inspect; manual Android/emulator cycles slow evidence collection. |
| **C. Small Step 5 testing shell, then X1, then full desktop client** | Adds deterministic host/join control, explicit reject reasons, state/event logging and late-join snapshot inspection using existing `megamod-join`/headless paths; emulator remains the real APK check | A bounded amount of shell/network plumbing, provided it does not grow native menus, audio or a new gameplay loop. X1 then informs full UI needs. |

**Recommend C.** Before X1, add only the testing seams needed to launch a headless host and two scripted joiners on one machine, issue a button-interact input through `hta_input`/the normal client intent, start a late joiner, and inspect door/collider/actor state plus host/join rejection diagnostics. Extend `megamod-join` or the existing harness; keep simulation in `hta_session_tick`, networking in the shared session/host code, and no frontend-specific event rule. If the current joiner cannot issue a real interact intent, add that small action path during X1, not a full desktop menu. Use emulator for Android-specific regression and at least one APK-to-desktop LAN check. Headless runs and dedicated-server direction both benefit from the same shared path.

**Stop line:** the testing shell is done when it can reproduce a successful join, a content-mismatch rejection, a late join and a scripted action with inspectable state. Full Step 5 parity (native menu, audio, local player presentation and all controls) follows X1; it is not an X1 prerequisite. This order improves tests without making a desktop frontend own world behavior.
