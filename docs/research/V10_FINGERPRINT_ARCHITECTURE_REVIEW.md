# Independent review: planned v10 gameplay compatibility fingerprint

**Status:** architecture recommendation, 2026-09-26; not an implementation claim. Read-only evidence: [`protocol.h`](../../src/net/protocol.h), [`content.c`](../../src/app/content.c), [`match_load.c`](../../src/app/match_load.c), [`host_net.c`](../../src/app/host_net.c), [`oal_asset.c`](../../src/asset/oal_asset.c), and the [N1 boundary review](CURRENT_RUNTIME_CONTENT_BOUNDARY_REVIEW.md). Claude owns the actual v10 codec and tests. This document describes the desired semantic contract and a reproducible candidate encoding, not a requirement to change its in-flight code blindly.

## Safety property and scope

Before a client may spawn, every numeric index in a packet that either peer interprets using locally loaded content must denote compatible content at that same index. Equal counts are insufficient. The fingerprint is a **per-match effective-content projection**: compute after selecting the world and building the weapon/character rosters, before accepting a join. It is not an install ID, source-package inventory, authentication token, or future X4 lockfile. Host and joiner must both have a valid nonzero fingerprint for the same profile/version; absent, zero, malformed, calculation failure, or mismatch rejects before spawn. No v9-style `if both nonzero` escape.

Current wire evidence: `WORLD.character` and `CONTROL.character` use character index + 1; `WORLD.weapon`, `carry`, `CONTROL.loadout`, `DROPS.weapon` and FX use the weapon roster; `PROJECTILES.pool` uses a projectile-pool index; `VEHICLES.index`, `GAME.hull`, `GAME.prop_broken`, and `WORLD.item_choice` refer to independently constructed ordered data. Weapon roster also contains vehicle triggers and hidden ability shots. Thus character/weapon matching is the urgent floor, not a proof that all ordinals are safe.

| Class | MUST MATCH before spawn | MAY DIFFER if tested independent | SHOULD NOT BE HASHED as identity |
| --- | --- | --- | --- |
| Character roster | Count and order; `kind`, exact internal `name`; resolved base/body gameplay template, health/shield/damage/speed/flying, unique limit, default loadout resolution, ability kind/base/damage/timing/radius/force/cone/beam and its resulting weapon slot | Cosmetic body mesh, texture, skin, voice, UI display only where it is not used as a lookup | Source path/URL, import time, warnings, raw source class, display label **only after** loadout lookup ceases to depend on it |
| Weapon roster, including built-in, imported, vehicle and hidden ability entries | Count and order; role (carry/vehicle/ability); exact internal identity or resolved Halo tag identity; base and effective fire mode, rate/spread, projectile behavior/pool assignment, damage/blast, ammo/reload/recharge, melee/knockback, mount movement and ability behavior | View/world mesh, animation and purely presentational crosshair, sound, muzzle flash, cosmetic skins | Source/staging file path, provenance, timestamps, presentation labels **only after** no gameplay lookup uses them |
| World and other indexed gameplay data | Existing world selection and map compatibility check, plus ordered breakable properties and bounds where `prop_broken` maps by bit; ordered pickup choices/placements, vehicle type/placement/seat and gun assignment, projectile-pool map, collision and spawn/flag semantics if local prediction or hosting uses them | Lightmaps, albedo textures, decorative non-solid models, weather particles if proven local only | Whole manifest JSON or package bytes solely to pick up provenance, warning, texture or importer-order changes |
| Rules/schema | Protocol/profile version, game-mode and gameplay rule definitions that are locally interpreted; fixed numeric enum meanings | Host-selected current score/time/state values that already arrive authoritatively | Diagnostics, logs, local filesystem root, memory addresses, C padding |

**Caveats from code:** `display_name` is a legacy lookup key for character loadouts, so it cannot yet be dismissed as cosmetic. `hold_type` and animation roles may affect binding/stance and need a call-site audit before exclusion. Projectile mesh geometry is likely presentation, but projectile collision radius, speed, blast and pool-to-weapon mapping are gameplay. Material enum values currently affect prop health/defaults and impact behavior; semantic material class belongs in the world projection when relevant, while texture pixels do not. `GAME` already sends broken prop state but its bit position refers to locally built props. A raw map manifest hash currently causes false rejection on provenance changes and is not a model for the new fingerprint.

### Read-only review of Claude's in-flight branch (uncommitted at review time)

The current `n-phase` draft is narrower than the candidate below: `compat.c` hashes loaded imported OALASSET character/weapon arrays with 64-bit FNV-1a, while the existing map CRC remains a separate gate. This closes the common same-position/different-asset case when both sides compute values. Before landing, review these concrete edges:

1. The in-flight `src/net/session.c` still checks `if (s->map_crc && ...)` and `if (s->content && ...)`. The explicit zero-zero harness exception allows a network-facing host with no initialized values to accept arbitrary joins. The user's mandatory/zero-bypass requirement calls for a separate harness mode or a synthetic nonzero harness fingerprint, not an implicit zero exemption on the production join path. Confirm both server and client values are valid before allocating a player slot.
2. The in-flight `src/app/compat.c` rounds floats to 1/10,000, clamps large values and maps NaN to one sentinel. Two distinct finite gameplay numbers can hash the same, and nonfinite inputs do not cause calculation failure. If exact compatibility is required, hash effective binary32 values (canonicalizing only `-0`) and fail closed on invalid numbers. A tolerance would need a demonstrated gameplay equivalence rule per field.
3. The draft hashes imported input arrays, not the final accepted `game.characters[]`, `game.weapons[]` and `game.pools[]`. The same Trial cache and roster-building code make many derived values identical today, but hidden ability shots, vehicle gun entries and pool ordinals should be explicitly tested and documented as covered by that invariant or added to the projection. `WORLD.item_choice`, vehicle and prop positions remain dependent on the separate map gate.
4. FNV-1a 64 is adequate for ordinary accidental mismatch detection but lacks deliberate collision resistance. This is not authentication; if untrusted packages can be chosen to pass a false match, use a cryptographic digest or document that threat as outside v10. More urgent than algorithm choice is eliminating zero/invalid bypass and omitted effective fields.

These are architecture review observations, not edits to the in-flight implementation; recheck after Claude commits because the draft can still change.

## Reproducible candidate for the immediate v10 index gate

The following **proposed** `MMCF/1` profile is intentionally bounded to the current match's world gate, characters, final weapon roster and projectile pools. It gives two independent implementations an identical byte stream. Claude's in-flight implementation may use a different profile, but must freeze its own byte layout and test vectors. This profile assumes the selected world's existing map/cache gate is made mandatory and nonzero; that legacy key also protects current vehicle, pickup and prop ordering. Its whole-manifest hash can over-reject on provenance changes and its 32-bit collision bound remains a known limitation. Replacing it with a semantic world projection is a later, separate schema change.

1. Compute SHA-256 over the stream below and transmit the full 32 bytes. Collision resistance is not mathematically needed for accidental drift, but SHA-256 is inexpensive at match load and avoids deliberate CRC/FNV collisions. It is **not** authentication. If the transport budget truly requires truncation, define a new profile using the first 16 bytes; never accept all-zero, missing or invalid digests.
2. Write exact ASCII `MMCF` (four bytes), `u16(1)`, `u16(10)`, then `u32(map_crc)` where `map_crc = cache.crc32 XOR world_ext.key` exactly as [`match_load.c`](../../src/app/match_load.c) currently computes it (zero `world_ext.key` for a Trial-only world). A zero map CRC is invalid. This is a transitional world compatibility key, not a claim that provenance is gameplay.
3. Primitive encodings: unsigned and two's-complement signed integers in little-endian declared width; boolean as `u8(0|1)`; `str` as `u32(UTF-8 byte count)` then exact bytes, no NUL, folding, normalization or replacement; `f32` as finite IEEE-754 binary32 little-endian with `-0` mapped to `+0`. Reject NaN, infinity, invalid UTF-8, overflow and unresolved content. A missing manifest value is first resolved through the **same loader/default** as gameplay, including the absent `body_shield = -1` sentinel; encode the effective value. Lists are `u32(count)` then entries in actual runtime index order, never sorted for hashing. No C padding, pointer, raw struct, native integer size or JSON decimal spelling enters the stream.
4. Encode `u32(character_count)`, then each **accepted** `game.characters[i]` in index order. Entry layout, in this exact order: `str(kind)`, `str(name)`, `str(display)` (currently used by display-name loadout resolution), `str(base)`, `str(loadout[0])`, `str(loadout[1])`, `f32(body_health)`, `f32(body_shield)`, `f32(body_damage)`, `f32(body_speed)`, `u8(can_fly)`, `f32(fly_speed)`, `f32(fly_damage)`, `str(hero_group)`, `i32(unique_limit)`, `str(ability_base)`, `f32(ability_damage)`, `f32(ability_cooldown)`, `f32(ability_duration)`, `f32(ability_interval)`, `f32(ability_radius)`, `f32(ability_force)`, `f32(ability_cone)`, `u8(ability_beam)`, `i32(game.char_ability[i])`. `ability_name` and `ability_color` are presentation in current behavior; if call-site audit finds gameplay use, revise the profile before shipping.
5. Encode `u32(weapon_count)`, then each **final** `game.weapons[i]` in index order, including built-ins, imported weapons, hidden ability shots and vehicle triggers. Entry prefix: `str(asset ? asset->kind : "halo")`, `str(asset ? asset->name : (hero ? hero->name : def.path))`, `str(def.path)` (internal Halo tag identity, not a source filesystem path), `str(display)` (legacy loadout lookup), `i32(base)`, `u8(vehicle)`, `i32(trigger)`, `u8(hidden)`, `u8(beam)`, `u8(melee_only)`, `u8(mount)`, `f32(knockback)`, `f32(damage_scale)`, `i32(pool)`, `f32(speed)`, `f32(blast_damage)`, `f32(blast_radius)`, `f32(blast_core)`, `u32(impact_jpt)`, `u32(melee_jpt)`, `f32(melee_damage)`, `u8(travels)`, `f32(autoaim_angle)`, `f32(autoaim_range)`, `f32(magnet_angle)`, `f32(magnet_range)`. Then encode the effective `def` gameplay fields in this order: `i32(zoom_levels)`, `f32(zoom_mag[0])`, `f32(zoom_mag[1])`, `f32(rof)`, `f32(cooldown)`, `f32(error_angle[0])`, `f32(error_angle[1])`, `f32(error_accel)`, `f32(error_decel)`, `f32(min_error)`, `i32(rounds_per_shot)`, `i32(projectiles_per_shot)`, `u32(projectile_id)`, `u32(firing_damage_id)`, `i32(rounds_loaded_max)`, `i32(rounds_reserve_max)`, `i32(rounds_initial)`, `i32(rounds_reloaded)`, `f32(reload_time)`, `f32(chamber_time)`, `f32(recharge)`, `f32(fp_offset[0..2])`, `u32(trigger)`, `u32(trigger_count)`, `u32(trigger_flags)`, `i32(magazine)`, `u32(mag_flags)`, `f32(rof_initial)`, `f32(rof_accel)`, `u8(single_shot)`. For imported weapons append `u8(1)`, then `str(asset->base)`, `u8(asset->mount)`, `f32(asset->fly_speed)`, `f32(asset->mount_offset[0..2])`, `f32(asset->mount_yaw)`, `f32(asset->mount_pitch)`; for others append only `u8(0)`. Array notation means consecutive scalar values in increasing subscript order.
6. Encode `u32(pool_count)`, then for each `game.pools[i]`: `i32(pool_weapon[i])`, `u32(proj_tag_id)`, `f32(speed_initial)`, `f32(speed_final)`, `f32(range)`, `f32(timer)`, `f32(gravity_scale)`, `u8(bounces)`, `u16(timer_starts)`, `f32(blast_radius)`, `f32(blast_damage)`, `f32(blast_damage_radius)`, `f32(blast_core)`. This binds transmitted pool numbers to physical behavior. The host-only fixed pool numbers 12/13 remain protocol constants and should be covered by a shared protocol version/test. The stream ends here; no trailing bytes.

This explicit profile deliberately includes a few legacy presentation strings that currently participate in gameplay lookup. Once lookup uses stable IDs, a new schema may omit them. Conversely, if a reviewed gameplay call site uses a currently omitted value, add it under a **new** profile/schema number and update test vectors; never change `MMCF/1` silently. The current map key's provenance coupling is a reason to replace the world projection later, not a reason to allow mismatched indexed content now.

**Caching:** cache only under a key covering selected world, all loaded gameplay input bytes/versions, load order, effective roster-building options and the projection schema. In-memory reuse for the same immutable match is safe; an install-wide cached value or stale file-mtime-only cache is not. Recompute after changing content or rules and before a new match. Future stable IDs can replace name/order fields only when packets actually carry resolved ID mappings or an agreed registry table; current ordinal fields stay order-sensitive until the wire format changes.

**Acceptance tests:** independent Android/desktop encoders produce the same known digest for one synthetic closure; swapping two same-count characters or weapons, changing a weapon stat, changing a hidden ability or pool owner, and reordering breakables all reject before spawn. A texture/provenance-only edit keeps the semantic digest if the relevant loader behavior is unchanged. Zero/failed calculation rejects. Late join uses the same match digest as initial join. These are recommendations for Claude's review, not tests added here.
