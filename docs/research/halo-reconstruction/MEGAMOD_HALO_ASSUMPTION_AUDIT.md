# MegaMod Halo assumption audit

This is an **ownership audit**, not a refactor request. It compares the 2342 [object/tag](https://github.com/bnunu/halo-1/tree/52659b6/source/objects), [scenario](https://github.com/bnunu/halo-1/tree/52659b6/source/scenario) and [game-rule](https://github.com/bnunu/halo-1/tree/52659b6/source/game) families with MegaMod's [current vision](../../MEGAMOD_VISION.md), [X1/X2 world entities](../../WORLD_ENTITIES.md), [runtime boundary review](../CURRENT_RUNTIME_CONTENT_BOUNDARY_REVIEW.md) and Open Asset Lab's [vision](https://github.com/madpai/open-asset-lab/blob/main/docs/ASSET_LAB_VISION.md). Classification is about concept ownership, not a mandate to rework landed X1/X2.

| Current MegaMod concept | Classification | Evidence and boundary |
| --- | --- | --- |
| Halo cache/tag parsing, `tag_id`, tag paths, Trial scenario equipment and resource maps | **KEEP IN HALO COMPATIBILITY LAYER** | 2342 cache/scenario/tag code is Halo-specific; MegaMod's `asset/` reads Trial tags. Generic runtime definitions should receive resolved data. OAL should preserve source provenance, not emit Halo tag IDs as universal IDs. |
| Loading Blood Gulch tags even for an imported match | **SHOULD EVENTUALLY BE GENERALIZED** | [Vision §4](../../MEGAMOD_VISION.md) identifies this current bootstrap dependency. Original-content support needs independent character/weapon/sky/rule definitions; no immediate port-driven change. |
| `hta_` symbol prefix | **GENERIC ENGINE CONCEPT ALREADY EXISTS** | Historical naming only; [vision](../../MEGAMOD_VISION.md) explicitly says keep it. Renaming has no product value. |
| Specialized unit, vehicle, projectile, prop and effect pools | **GENERIC ENGINE CONCEPT ALREADY EXISTS** | The pool shape is useful; the 2342 datum array reinforces stale-slot hazards. Keep specialized storage. X1 world entities now have checked generation handles; other pools need them only when a real cross-system feature requires them. |
| Dense roster, projectile-pool, prop and vehicle ordinals in local state/wire fields | **SHOULD EVENTUALLY BE GENERALIZED** | [v10 dense-index audit](../DENSE_INDEX_HAZARDS.md) documents remaining ordinal risks. X2's [world key](../../WORLD_ENTITIES.md#world-compatibility-x2) now covers played binary world data, closing the earlier same-manifest geometry gap for the current schema. Stable authored IDs, checked runtime handles and explicit wire identities must still be distinguished. |
| Halo object type masks and parent/child type tree | **KEEP IN HALO COMPATIBILITY LAYER** | Useful to interpret Halo data; generic world objects should use capabilities/definitions suited to authored content rather than inherit Halo's twelve type ordinals. |
| Weapon trigger, ammo, projectile, melee, explosion and damage concepts | **GENERIC ENGINE CONCEPT ALREADY EXISTS** | These are reusable gameplay concepts. Trial tag decoding and exact Halo flags remain in compatibility; Showdown balance is independent. |
| Halo-only weapon timing, animation roles and `jpt!` damage interpretation | **KEEP IN HALO COMPATIBILITY LAYER** | The reconstruction can guide Trial tests, but generic `WeaponDefinition` and damage/surface classes must not require Halo tag fields or clip names. |
| Player assumed to be a Halo biped with two carried weapons | **SHOULD EVENTUALLY BE GENERALIZED** | Showdown already has imported characters and powers; vision calls for generic character/loadout definitions. Some current `game.c` paths still begin with Trial biped/weapon data. |
| Vehicles only from Blood Gulch palettes and Halo seat tags | **SHOULD EVENTUALLY BE GENERALIZED** | Current engine can simulate vehicles, but [vision §4](../../MEGAMOD_VISION.md) says imported/original vehicle content is not yet general. Halo seat tag interpretation stays local. |
| Slayer/Team/CTF hard-coded game modes and red/blue team enum | **SHOULD EVENTUALLY BE GENERALIZED** | Generic objectives and teams are a [future vision](../../MEGAMOD_VISION.md), not present capability. The Halo game-engine mode tree shows one way a specific title coupled rules to player/object state; copying it would not unlock user-authored games. |
| Halo sky on imported worlds and Halo material/shader interpretation | **SHOULD EVENTUALLY BE GENERALIZED** | Both are named bootstrap couplings in [vision](../../MEGAMOD_VISION.md). OAL already compiles foreign maps; a generic material/sky contract is still future work. |
| Fixed pool sizes and protocol caps | **UNCLEAR** | Capacity must be explicit and tested. The 128-player fork demonstrates wide coupling, but does not prove MegaMod needs dynamic allocation or bigger limits now. Tie changes to measured content/session needs. |
| Xbox save-game memory image, XDK platform interfaces, Direct3D8 state, HS VM | **SHOULD EVENTUALLY BE REMOVED** **only if such artifacts enter generic code** | They are absent as intended generic requirements today. Keep the boundary explicit: future saves, Lua and Vulkan should have MegaMod contracts. |

## What should not influence MegaMod Engine

1. The Xbox's 2001 fixed memory map, 32-bit pointers, 2048-object cap and tightly coupled game-state image. They served that product and hardware; the port's elaborate Android guest/host bridge is a compatibility cost, not a portable-engine template. [Capacity reference](https://github.com/bnunu/halo-1/blob/52659b6/docs/common_constants.md), [Android port notes](https://github.com/cybersecurity/halo-ce-universal/blob/13d1ae2/port/android/README.md#why-the-game-is-not-an-ordinary-arm64-library).
2. Halo's object inheritance/masks, encounter/AI script machinery, exact tag schema and proprietary content assumptions as generic runtime primitives. These belong to compatibility analysis only.
3. Xbox rasterizer/Direct3D8 emulation, shader translation and UI layout as a model for MegaMod Vulkan. The port solved preservation constraints that MegaMod does not share.
4. Original system-link lockstep, 4-machine/16-player limits, or the fork's 128-player target as a reason to replace v10 host authority. The fork's measured quadratic upload cost is a caution, not a feature request.
5. Byte-match progress as evidence of better engine architecture. It measures fidelity to a particular binary. It does not measure usefulness for original content, OAL packages, testability, or maintainability.

**Roadmap consequence:** none. X1 and X2 are landed; keep Lua and original-content work driven by MegaMod feature needs. Put only independently verified Trial-compatible behavior in the Halo layer; keep Showdown's deliberate departures labelled as game rules.
