# Portability, networking and agent-development lessons

Findings distinguish original reconstructed 2342 code from the **new universal port** and the later **128-player fork**. No port code should move to MegaMod. Evidence labels use the requested vocabulary; recommendations are documentation or independent tests only.

## Portability

| Finding and MegaMod relevance | Source / target / evidence / confidence / action |
| --- | --- |
| The universal port isolates Xbox APIs behind [SDL3, OpenGL and POSIX shims](https://github.com/cybersecurity/halo-ce-universal/blob/13d1ae2/port/linux/README.md), with Windows-specific [file, network and memory adapters](https://github.com/cybersecurity/halo-ce-universal/blob/13d1ae2/port/windows/README.md). Filesystem semantics, path translation, ABI/calling convention, time, input, audio and graphics all caused work. MegaMod already has platform-specific Android/desktop layers and a Vulkan renderer; audit each new game API for file/time/input assumptions rather than adopting an Xbox SDK shim. | cybersecurity/halo-ce-universal; 2342-derived native port; **PORT IMPLEMENTATION**; **HIGH**; **DOCUMENT**. |
| Its native renderer preserves 30 Hz simulation while drawing at display refresh, using previous/latest object, camera and first-person poses. It snaps discontinuities such as teleports or camera cuts, and acknowledges a one-tick visual delay. This supports an independent MegaMod test of interpolation around respawn, teleport, seat entry and late join; it does not prescribe the same delay or renderer. [Port source](https://github.com/cybersecurity/halo-ce-universal/blob/13d1ae2/port/linux/game/render_interpolation.c). | cybersecurity/halo-ce-universal; native port, not Xbox matching build; **PORT IMPLEMENTATION**; **HIGH**; **ADD TEST**. |
| The Linux port documents an inline-header discrepancy that changed view visibility only under clang, while the matching MSVC build did not expose it. Cross-compiler parity and a real-view fixture matter; byte matching alone is insufficient to validate another target. [Port investigation](https://github.com/cybersecurity/halo-ce-universal/blob/13d1ae2/port/linux/README.md#game-source-edits). | cybersecurity/halo-ce-universal; native port; **PROJECT DOCUMENTATION**; **MEDIUM**; **DOCUMENT**. |
| Android is unusually hard because Xbox cache/save layouts and Direct3D resources embed 32-bit pointers. The port runs ILP32 AArch64 game code as a guest inside a 64-bit NDK host, with an import table, fixed low address window, ABI checks and custom C library. It currently requires 4 KB pages and controller/keyboard input. [Android design and limits](https://github.com/cybersecurity/halo-ce-universal/blob/13d1ae2/port/android/README.md#how-it-works). MegaMod's ARM64 Vulkan/AAudio design is independent, so **do not copy the guest/host mechanism**. The general lessons are to keep serialized formats pointer-free, validate ABI boundaries, support Android storage import, exercise Android-only builds and log actionable native failures. | cybersecurity/halo-ce-universal; Android port; **PORT IMPLEMENTATION** + **PROJECT DOCUMENTATION**; **HIGH**; **DOCUMENT**. |

MegaMod's [shared-session desktop plan](../../DESKTOP_AGENT.md) and [engine map](../../ENGINE_ARCHITECTURE.md) already aim at one simulation with platform adapters. The universal port is a stress case for **hidden assumptions**, not an architecture to emulate. Android-specific checks worth retaining: file permission/storage flow, 64-bit page-size and alignment assumptions, controller/touch parity, surface loss/recreation, frame pacing, and host-vs-device numeric drift. Some of these are port-derived risk hypotheses, not observed MegaMod bugs.

## Networking and the 128-player fork

| Finding and MegaMod relevance | Source / target / evidence / confidence / action |
| --- | --- |
| Reconstructed managers distinguish machine and player identity and [reliable/unreliable channels](https://github.com/bnunu/halo-1/blob/52659b6/source/networking/network_connection.c). The [server tick](https://github.com/bnunu/halo-1/blob/52659b6/source/networking/network_server_manager.c#L1697-L1746) sends numbered player updates, time and seed; the [client](https://github.com/bnunu/halo-1/blob/52659b6/source/networking/network_client_manager.c#L1631-L1707) checks sequence and seed. The fork documents lockstep across peers. This is conceptually different from MegaMod's v10 host-authoritative simulation and snapshots; retain MegaMod's authority model. | bnunu/halo-1 plus bnunu/halo-ce-universal; Xbox 2342 lineage/port; **RECONSTRUCTED SOURCE** + **PROJECT DOCUMENTATION**; **MEDIUM**; **DOCUMENT**. |
| The base universal port did **not** yet have the 128-player feature at examined revision. The bnunu fork changes 16 players/4 machines to 128/128 in the **native port**, with a versioned incompatible protocol. It enlarges game-state memory (~3.3 to 16 MB), object/effect/particle/sound pools, player/machine arrays, packet buffers, game-setting fragmentation, signed field widths, UI and scoring assumptions. This demonstrates that limits form a cross-system contract, not one constant. [System-link report](https://github.com/bnunu/halo-ce-universal/blob/f2fa457/port/linux/README.md#system-link), [limit definitions](https://github.com/bnunu/halo-ce-universal/blob/f2fa457/port/linux/include/halo_port_limits.h), [capacity definitions](https://github.com/bnunu/halo-ce-universal/blob/f2fa457/port/linux/include/halo_port_capacity.h). | bnunu/halo-ce-universal; 2342-derived **port only**; **PORT IMPLEMENTATION** + **PROJECT DOCUMENTATION**; **HIGH**; **DOCUMENT**. |
| The fork reports ~3.9 KB of all-player input per tick at 128 players, about 0.9 Mbit/s to each machine and 118 Mbit/s host upload for 128 machines; game-state pools must match to preserve lockstep. These are **fork measurements**, not universal networking laws or MegaMod targets. [Traffic notes](https://github.com/bnunu/halo-ce-universal/blob/f2fa457/port/linux/README.md#system-link). A future MegaMod scale review should measure packet size, per-client update work, reliable-queue growth and late-join state at its own intended limits. | bnunu/halo-ce-universal; native fork; **PROJECT DOCUMENTATION**; **MEDIUM**; **ADD TEST** only when scale work is scheduled. |
| The fork's lightweight [system-link bots](https://github.com/bnunu/halo-ce-universal/blob/f2fa457/tools/system_link_bots.py) join and acknowledge ticks without running full simulation. This is useful **test methodology**: protocol clients can stress joins, caps and timeouts, but cannot prove rendered or simulated gameplay correctness. MegaMod already has synthetic network tests and a planned desktop playtest harness. | bnunu/halo-ce-universal; native fork; **PORT IMPLEMENTATION**; **HIGH**; **DOCUMENT**. |

The original limit likely reflects multiple factors: four local controllers/machine, fixed arrays and UI, 2001 memory and network budget. The fork proves which **implementation** boundaries had to change; it does **not** prove Bungie's historical rationale or an arbitrary-only cap. The reconstructed [server has an in-game player addition path](https://github.com/bnunu/halo-1/blob/52659b6/source/networking/network_server_manager.c#L1743-L1777), but full mid-match world-state joining, object-replication semantics and late-join guarantees were not resolved in this pass. Do not infer a generic network object-ID system from datum handles. MegaMod v10's [dense-index hazard audit](../DENSE_INDEX_HAZARDS.md), [X2 world key](../../WORLD_ENTITIES.md#world-compatibility-x2) and [content-compatibility contract](../../CONTENT_COMPATIBILITY.md) remain the actionable local evidence.

## Agent development practices

| Finding and MegaMod relevance | Source / target / evidence / confidence / action |
| --- | --- |
| The reconstruction fork has a short [house-rules index](https://github.com/bnunu/halo-1/blob/52659b6/docs/campaign_house_rules.md), [constants/types map](https://github.com/bnunu/halo-1/blob/52659b6/docs/common_constants.md), [assertion contract](https://github.com/bnunu/halo-1/blob/52659b6/docs/assertions.md), [source map](https://github.com/bnunu/halo-1/blob/52659b6/docs/user_source_reconstruction_map_20260906.md), and [matching/credibility method](https://github.com/bnunu/halo-1/blob/52659b6/docs/matching_methodology.md). Agents can find an owner, check a constant, and state evidence quality before editing. MegaMod's `AGENTS.md`, `CLAUDE.md`, handoff, journal, skills and verify scripts already do much of this; the missing opportunity is a **short, machine-readable capability/API index** with authority, input/output, sample fixtures and error codes for each engine verb. | bnunu/halo-1; reconstruction campaign; **PROJECT DOCUMENTATION**; **HIGH**; **DOCUMENT**. |
| Its methodology separates verified exact matches, credible fuzzy reconstructions, cross-build hints and unsupported claims. It parks uncertain work and tracks regressions in ledgers. MegaMod/OAL should likewise label **observed Trial**, **tag-derived**, **inferred**, **invented for Showdown**, and **verified generic** in test reports and agent-facing documentation. OAL already carries provenance and inferred-value labels; extend the same language to engine capability docs when useful. | bnunu/halo-1; reconstruction campaign; **PROJECT DOCUMENTATION**; **HIGH**; **DOCUMENT**. |
| The 128-player fork's stand-in clients illustrate bounded task decomposition: one can validate protocol joins and throughput without launching full clients, then separately run real simulation/render tests. MegaMod's desired agent loop should expose discoverable capabilities, compile/validate, headless launch, scripted control, structured events and packaging as separate commands with deterministic fixtures. This follows the [desktop agent plan](../../DESKTOP_AGENT.md); it is **not** a new implementation project from this research. | bnunu/halo-ce-universal + MegaMod; port/test tooling; **INFERENCE**; **MEDIUM**; **DOCUMENT**. |

Do not copy byte-matching campaign rules into ordinary MegaMod feature development. The transferable habit is **evidence hygiene**: clear owner maps, reproducible gates, explicit confidence, rejection of fabricated correctness and concise handoffs. Agent autonomy needs structured outputs and a stable API boundary, not reconstruction-specific compiler tricks.
