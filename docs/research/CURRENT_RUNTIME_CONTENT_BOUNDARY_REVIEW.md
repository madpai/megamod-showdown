# N1 independent boundary review

**Status:** source observation, 2026-09-26; supports Claude's contract inventory, not a replacement for it. Checked MegaMod `halo-sandbox` and Open Asset Lab `main` as present locally on this date. No package or runtime behavior was changed.

## Field roles at the current boundary

| Current field/path | Current role | Evidence and caution |
| --- | --- | --- |
| OALMAP `map_id`, `display_name` | Intended authored identity; menu label | [OAL compiler](https://github.com/madpai/open-asset-lab/blob/main/assetlab/package.py) defaults `map_id` from the BSP stem and emits both. MegaMod's [world loader](../../src/app/content.c) chooses `maps/<s->world>.oalmap` and does not compare that filename to `map_id`. `map_id` is therefore **not yet an enforced runtime ID**. |
| OALMAP `source_reference`, `source_sha256`, `source_format`, `source_provenance`, raw `entities`, material paths | Provenance and authoring diagnostics; incidental network-key input | Emitted by `compile_map`; the runtime does not use these as behavior instructions. **Their bytes still affect `world_ext.key` because it hashes the whole manifest**, so a provenance-only change can currently change map matching. Raw source class/keyvalue records must stay outside a generic world-entity contract. |
| OALMAP vertices, indices, groups, textures, binary spawns | Compiled content | [OALMAP adapter](../../src/asset/external_map.c) bounds-checks and copies these to mesh/spawn structures. Group flags encode collision, alpha and breakable index plus one; indices are package-local positions, not stable IDs. |
| OALMAP manifest `spawn_points.team`, `flag_points`, `breakables`, `weather` | **Compiled gameplay content inside JSON** | The [map adapter](../../src/asset/external_map.c) scans these known keys at load. The `RUNTIME_PACKAGE.md` claim that runtime skips manifest JSON was too broad and is corrected in OAL. The scans rely on canonical key spelling and ordering; N1 should record this as a real contract. |
| OALMAP `breakables[].index`, group breakable bits | Package-local reference/ordinal | Compiler assigns order while emitting groups; runtime maps groups to breakable slots. Reordering the compiler's breakable list can change the meaning of replicated prop indices even if visuals look the same. |
| OALASSET `kind`, `name`, `display_name` | Type discriminator; partial authored ID; menu label | [Asset builder](https://github.com/madpai/open-asset-lab/blob/main/assetlab/character.py) writes `kind` and `name`; [runtime parser](../../src/asset/oal_asset.c) copies them into fixed-size fields. `name` lacks package ownership and is capped by a 48-byte C buffer. Some UI paths compare it directly; weapons are often selected by `display_name`. A future 96-byte canonical ID needs its own storage, not silent reuse of this field. |
| OALASSET `base`, `ability_base`, `loadout[]` | Compiled gameplay references with legacy lookup semantics | [Game registration](../../src/game/game.c) matches bases with substring searches in Halo tag paths and matches loadout strings to weapon display labels. These are not validated canonical references; display renames or ambiguous substrings can change behavior. |
| OALASSET stats, clips, models, sounds, attachment roles | Compiled definitions and media | Runtime parses gameplay numbers from manifest, then loads model/audio data. Clip and attachment names are semantic lookup keys within a model, not package identities. Some source skeleton names still appear in the [imported weapon binding](../../src/game/imported.c). |
| `hta_oal_asset` pointers, `g->weapons[]`/`g->characters[]`, `hta_prop` health/broken/respawn | Runtime definition references and mutable instance state | [Game registration](../../src/game/game.c) appends assets and cloned Halo weapons into dense arrays; [props](../../src/engine/props.h) own live damage/collision. Array positions and pointers are runtime handles, not authoring IDs. |
| `s->world`, `external.oalmap`, sorted `characters/` and `weapons/` filenames | File/selection identity | [Content loading](../../src/app/content.c) and [filesystem](../../src/app/fs.c) use path lookup, first root wins, and sorted deduplicated filenames. Duplicate filenames across roots are silently hidden; different filenames may carry duplicate manifest names. |
| `world_ext.key`, `cache.crc32`, imported roster indices, prop bit positions | Current network matching/encoding | [World key](../../src/asset/external_map.c) is FNV-1a of manifest bytes. [Match begin](../../src/app/match_load.c) XORs it with Trial cache CRC. [HELLO](../../src/net/session.c) rejects unequal *nonzero* CRCs, so it is neither a complete package closure check nor a cryptographic identity. [Filesystem contract](../../src/app/fs.h) explicitly relies on filename sort for roster index consistency. [GAME packet](../../src/net/protocol.h) sends prop broken bits by dense ordinal. |

**Source observation:** the compiler already emits `missing_dependencies`, warnings and source provenance, but runtime validation concentrates on binary bounds and supported format versions. OAL is the right place to validate source references and duplicate authored identities; the runtime still has to reject malformed or unsupported compiled data.

## N1 questions Claude should retain in the contract inventory

1. Which values currently form the *actual* join compatibility requirement: Trial cache CRC, exact OALMAP manifest bytes, roster filenames/order, and any OALASSET gameplay values? The current HELLO check covers only the first two and permits a zero CRC on either side.
2. Which map-manifest JSON keys are truly runtime inputs? `spawn_points.team`, `flag_points`, `breakables`, and `weather` are; raw `entities` and provenance are not. The exact parser assumptions matter until a typed section exists.
3. Which legacy references must be migration aliases? Distinguish `s->world` path stem, asset `name`, display-name loadouts, Halo tag-path substrings, and prop ordinals. None should silently become a canonical save ID.
4. Does the local content set contain duplicate asset `name` values under different filenames, duplicate display labels, or substring-ambiguous Halo bases? A read-only inventory can answer this without changing formats.

**Inference:** N2 can begin with validation/reporting on existing manifests and a separate canonical ID field. A binary redesign is unnecessary for that proof. N3 should measure how much of the gameplay closure is outside the present map CRC before treating that CRC as package compatibility.
